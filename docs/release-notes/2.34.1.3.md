# OpenTok.Net.Android 2.34.1.3

Adds a third package. The native SDK is unchanged at `opentok-android-sdk` 2.34.1, and
`OpenTok.Net.webrtc.Dependency.Android` is unchanged at 121.1.101.1.

## New: `OpenTok.Net.Transformers.Android`

Background blur, background replacement and audio noise suppression.

```bash
dotnet add package OpenTok.Net.Transformers.Android
```

`PublisherKit.VideoTransformer`, `PublisherKit.AudioTransformer`, `SetVideoTransformers` and
`SetAudioTransformers` have been in `OpenTok.Net.Android` all along — but the implementations live
in a separate library Vonage ships as an opt-in Gradle dependency
(`com.vonage:client-sdk-video-transformers`), which nothing shipped. Constructing a transformer
therefore compiled, linked, and then returned null at runtime with

```
0x0A000006 — MediaTransformerOpenTokTransformersLibraryNotLoaded
```

a value that has been sitting in this binding's own `OpentokError.ErrorCode` enum the whole time.

This restores the capability the predecessor monorepo had as
`OpenTok.Net.mltransformers.Dependency.Android`, which the restructure dropped.

The package carries **three** Maven artifacts, not one — see
[`src/OpenTok.Transformers.md`](../../src/OpenTok.Transformers.md). The main `.aar` is
self-contained as far as native code goes, but `mltransformers-ps16k` carries
`libVonageSelfieSegmentation_android_lib.jar` — 159 MediaPipe classes plus the native loader — which
the background transformers reach through JNI. Shipping only the main `.aar` would fail with
`NoClassDefFoundError` instead.

The `-ps16k` suffix on both ML libraries is the 16 KB page-size build, which Android 15 requires on
64-bit devices, and it is what the transformers artifact's own POM declares. Verified against the
published artifacts: every `.so` in the 64-bit ABIs reports `PT_LOAD` alignment `0x4000`.

It has no managed API of its own and does not depend on the binding — add it alongside, if you want
the feature, for about 70 MB.

## Upstream drift now watches the transformers

Three new rows in `build/upstream.tsv`, in their own reporting group so a transformers-only bump
does not reopen the SDK issue and vice versa: the transformers artifact's availability, and the two
ML library versions as derived pins against its POM (the same treatment `WebrtcVersion` gets).

The availability check earns its place: Vonage has published an SDK version without a matching
transformers build before, and the first sign of it would otherwise be `BuildNugets.sh` failing to
resolve the artifact.

## CI: a Release packaging check on pull requests

New `transformers-packaging` job, on pull requests only — a release re-runs nothing, because the
tagged commit already passed it on its own PR.

It builds the device tests in **Release** with the transformers package and inspects the resulting
APK for the three `.so` files under `lib/arm64-v8a/` and the three `.tflite` models. Nothing else in
the pipeline can reach this: the package tests read the `.nupkg` and so only see what was packed,
and the emulator smoke tests build Debug and do not reference the package at all. What happens in
between is where it goes wrong — a Release build runs r8 and the Android packaging step, and a
native library dropped because nothing appears to reference it (exactly the shape of a payload-only
package) produces an APK that installs and then dies with `UnsatisfiedLinkError`.
